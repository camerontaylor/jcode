## Conflicts

Three files conflicted, 6 hunks. All are one decision: upstream `f3f11ab74`
built its own "apply `--model` when attaching to a running server" feature,
which the fork already has.

| | Fork (`startup_model`) | Upstream (`initial_model_spec`) |
| --- | --- | --- |
| Spec builder | `provider_init::startup_model_spec_with_profile`: recognises explicit routes (known provider prefixes, OAuth labels, compatible profiles, config providers), maps Azure to `azure-openai`, keeps named compatible profiles | `dispatch::client_initial_model_spec`: any `:` counts as a route, profile prefix, else `provider:model` |
| When | Every launch, so a newly spawned daemon also starts credential-free and the client selects the model after Subscribe | Only when a server is already running |
| Apply | `remote_followups` sends `SetModel`, tracks its request id with a timeout, and holds the first prompt until it is acknowledged; failure restores the input | `handle_post_connect` calls `remote.set_model` once and logs a failure |

Decision:

- `src/cli/tui_launch.rs` and `src/cli/ssh.rs`: kept the fork's
  `startup_model` parameter and `set_startup_model` call.
- `src/cli/dispatch.rs`: took upstream's `initial_model_spec` guard and its two
  "provider-only flags" messages, which now describe the fork's behaviour
  correctly. Passed the fork's `startup_model` to `run_tui_client`. This
  shrinks the fork's footprint in `dispatch.rs`.
- Upstream's `pending_initial_model_spec` field, `set_initial_model_spec`, and
  the `handle_post_connect` hook in `jcode-tui` are kept byte-identical to
  upstream but are never fed, so only one `SetModel` is sent. Upstream's
  `client_initial_model_spec` test still runs.
- `src/cli/selfdev.rs` merged cleanly: both sides added the same trailing
  `None` argument.

## Risks and notes

1. **Retired todo intent label (fixed in this PR).** After `7e6b21927`,
   `IntentUnderstanding` rejects `"complete"`. v1.1.2001 still writes it into
   `<session>-plan.json`, and both plan loaders (`jcode_base::todo::load_plan`,
   `jcode_todo_policy::store` `read_or_default`) turn a parse error into an
   empty `TodoPlan`: the session would lose its picker title, user intention
   and intent state, and the next save would overwrite the file. Todo items,
   goals and transcripts are unaffected. An exact fleet survey on 2026-11-27,
   validating every todo file against the merged enum labels, found only this
   value: 107 occurrences in plan files on pluto, uranus, atlas, triton and
   ceres, including Ceres files written 2026-11-26 by the deployed build; no
   numeric legacy scores. `fork_legacy.rs` (fork-owned) maps `"complete"` to
   `"clear"` on read, and the next save writes the current label. The hook is
   one call in the `semantic_state!` deserializer plus the module line;
   upstream's `states_reject_invalid_and_numeric_values` asserts the upgrade
   instead of the rejection. Numbers and other states stay rejected.
   Candidate to send upstream.
2. Self-dev sessions now get upstream's instruction to build and live-reload
   by default (`410425e66`). This applies only to jcode self-dev sessions.
